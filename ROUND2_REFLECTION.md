# Round 2 Reflection

## 1. What was the most uncomfortable trade-off you made because of the time pressure?

The decision to compare JSON snapshots instead of building live price scraping was the hardest cut. I knew from the start that a proper system would scrape vendor pricing pages on a schedule, parse the data, and detect changes against a ground truth. That's the version I'd want to ship. But scraping is inherently fragile — Cursor's pricing page uses dynamic React rendering, Anthropic restructured their pricing layout twice in 2025, and GitHub Copilot's pricing lives behind auth-gated docs. Building reliable parsers for even three vendors would've eaten 8+ hours, leaving no time for the diff UI or email pipeline. I decided around hour 4 of Day 1, when I was sketching the detection engine: compare stored JSON snapshots against the current `PRICING_DATA` constant, and let an admin endpoint handle manual updates. It means pricing changes are only detected when someone (or a future automation) explicitly updates the data. That's a real gap. But for 36 hours, the admin endpoint makes the gap manageable — an operator can update and trigger detection in under a minute.

## 2. If we extended the deadline another 24 hours, what's the first thing you'd do?

I'd build proper audit versioning. Right now, when a user clicks through from the pricing change email, the diff page re-runs the audit engine on-the-fly against current pricing. That's fine for display, but the result isn't persisted — if pricing changes again before they return, they'd see a different diff. With 24 more hours, I'd add a `reaudit_results` table that stores each re-run as an immutable row linked to the original audit. The diff page would first check for a stored re-run for the current pricing version and only compute fresh if none exists. I'd also add a "Save this re-audit" button on the diff page that persists the result and updates the `reaudit_count` on the original audit. The data model is already shaped for this — `reaudit_count` exists in the schema but is never incremented. It would take about 4 hours for the table, the persistence logic, the button, and a basic test.

## 3. Looking back at your Round 1 codebase, what did Round 1-you make harder for Round 2-you?

The biggest friction came from `PRICING_DATA` not being versioned from the start. In Round 1, pricing was a static constant — no version string, no snapshot system, no way to know which pricing a given audit was computed against. When I started Round 2, the first thing I had to build was the entire snapshot infrastructure: a `pricing_snapshots` table, a `PRICING_VERSION` constant, auto-seeding logic in `getLatestPricingSnapshot()`, and a migration to add `pricing_snapshot_id` to the existing `audits` table. That was 3+ hours of foundational work before I could write a single line of detection logic. If Round 1 had stored a pricing version hash alongside each audit — even just a timestamp or a content hash of the pricing array — Round 2's detection engine could have been a simple "compare the hash" check instead of a full snapshot comparison system. The audit result also didn't include a `created_at` timestamp in its own data structure (it relied on the Supabase row timestamp), which meant the diff view had to join against the database row rather than reading it from the result payload.
